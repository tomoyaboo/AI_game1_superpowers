## 1. 意図と背景

`Superpowers` を使った Claude Code × Codex の協調開発ワークフローを、実在プロジェクト
`VoidSurvival_10-Days`（衛星データ連動のUnityサバイバルアクション、デモ仕様書 v0.3）を
題材に検証する。検証で終わらせず、実際に **DemoSpec v0.3 で未着手とされている機能を実装し、
最終的に iPhone 上で動く状態にする** ことを目標にする。

参照資料: `docs/ai-handoff.md`（移動機能のリバースエンジニアリング結果）、
`docs/VoidSurvival_DemoSpec_v0.3.md`（git管理外、ローカル参照のみ）。

## 2. 目標・非目標・やらないこと

### 目標
1. DemoSpec v0.3 §5.6, §6, §7, §11.3, §11.4 に挙がっている未着手・既知バグを実装する
2. `docs/ai-handoff.md` の C-1〜C-6（移動系の課題）を解消する
3. 最終的に iOS（iPhone）向けビルドが実機/シミュレータで動く状態にする

### 非目標（今回は扱わない）
- 新規ストーリー・会話内容の追加（既存のDemoSpec/カット割りの範囲を超える創作）
- 新規アート制作（スプライト・エフェクトの新規作成。既存アセットの流用のみ）
- 衛星データの本番運用まわり（PlayFab側の設定変更等）

### 絶対にやらないこと（制約）
- **`NakaAwjr/VoidSurvival_10-Days`（upstream）への push・merge・PR は一切行わない。**
  `vendor/VoidSurvival_10-Days` は `.git` を削除済みで、upstream への経路自体が存在しない
- 既存の企画書（`docs/VoidSurvival_*.md`）をこのpersonalリポジトリにコミットしない（`.gitignore`済み）

## 3. 検討した進め方（Approaches）

| 方式 | 内容 | 採用 |
|---|---|---|
| A. 手渡し型 | Claudeが仕様書だけ書き、人間が手動でCodexを実行 | 不採用（遅い） |
| B. 完全自動ループ | Claudeがタスク分割→`codex exec`実行→差分レビュー→次へ、を人間の介在なしで連続実行 | 不採用（安全弁が無い） |
| **C. 自動ループ＋節目ごとの確認** | Bと同じだがタスク（機能単位）が1つ終わるごとに差分を提示し、次へ進めるか確認する | **採用** |

## 4. 決定した「どう作るか」

- **実行環境**: `codex exec`（非対話、`workspace-write` サンドボックス）を Claude Code から
  `Bash` ツール経由で呼び出す。作業対象は `vendor/VoidSurvival_10-Days/`
- **ブランチ戦略**: `vendor/` 配下に `.git` は無いため、ブランチは **親リポジトリ
  (`AI_game1_superpowers`) 側**で切る。タスク単位で `codex/<task-slug>` ブランチを作成し、
  Codexの変更を確認後 `main` にマージしてpush する
- **コミット方針**: タスクが完了するたびに、親リポジトリに意味のある単位でコミット・push する
  （「都度都度作業の状態が分かるように」という要望への対応）
- **レビュー方針**: Codexの変更は毎回 `git diff` で確認し、意図しない変更（スコープ外のファイル、
  upstream由来の生成物の巻き込みなど）が無いかをClaude Codeが見る
- **トークン/利用上限の監視**: CodexにもClaude Codeにも残量を直接問い合わせるAPIは無い。
  `codex exec` がレート制限/利用上限のエラーを返した場合、またはClaude Code側で制限に
  達した場合、その時点で即座に報告する（事前の残量監視はできない）

## 5. 実装順序

DemoSpec §12.2 の週次計画（1週目: 基盤・バグ修正／2週目: データ連携・端末UI／
3週目: リスポーン・現象実装・中継局／4週目: 調整）を踏襲し、依存の少ない順に並べた。

| # | タスク | 対応する課題/章 |
|---|---|---|
| 1 | 既知バグ修正 + `FlagData` 永続化（コンパイル確認のみ。自動テストは#2整備後に遡って追加） | DemoSpec §11.4(1,2,6,7), §7.9 |
| 2 | **自動テスト基盤（Unity Test Framework）** — `Assets/VoidSurvival_10-Days/Scripts/` を asmdef化し、Tests/EditMode asmdefから参照できるようにする | ai-handoff.md C-6 |
| 3 | 衛星データ→施設の接続（電圧→加工速度、電流→ドロップ率等） | DemoSpec §5.6 |
| 4 | 天候判定の3軸化（明暗/荒れ/計器信頼性） | DemoSpec §5.3 |
| 5 | リスポーン実装 | DemoSpec §11.3 |
| 6 | ESD（帯電・放電）・SEU（ビット反転）実装、移動側 `IsInversion` 接続 | DemoSpec §6, ai-handoff.md C-3 |
| 7 | 予報端末・中継局 | DemoSpec §7 |
| 8 | ZONE-N のエリア分割（手前/中間/奥） | DemoSpec §8.3 |
| 9 | 移動系の残課題（C-1 スタミナのフレーム依存, C-2 PCダッシュ割当, C-4 慣性ゼロ化） | ai-handoff.md |
| 10 | iOS ビルド対応（署名・サンドボックス・実機/シミュレータ確認） | 今回の最終目標 |

> **#1→#2の順序について**: 実際にコードを調べた結果、既存スクリプトは全て無印の
> `Assembly-CSharp` に属しており、Unity Test Framework で意味のある単体テストを書くには
> `Scripts/` を独自の asmdef に切り出す必要があると判明した（低リスクだが影響範囲が広い
> 構造変更）。これを最初のバグ修正に混ぜると診断が難しくなるため、#1は手動トレース＋
> コンパイル確認のみで済ませ、#2で専用タスクとしてテスト基盤を整備する。
>
> ゲームデザイン上の数値決定が必要な項目（武器Power、クラフト必要素材など、
> DemoSpec §11.4(3,4,5)）は、どのタスクにも含めず別途確認してから着手する。

各タスクの詳細な作業計画は、着手直前に `superpowers:writing-plans` で個別に作成する
（今回は #1 から着手）。

## 6. ビルダー（Codex）に委ねること

- 各タスクの具体的なコード変更（クラス設計・メソッド分割・命名）はCodexの裁量とする
- 既存のコードスタイル・既存クラスの責務分担（`CharacterStatus`/`PlayerStatus`等の継承構造）を
  変えない範囲での実装を基本方針とする。構造を変える必要がある場合は提案として報告する
